# Open Knowledge Format (OKF)

**Version 0.2**

OKF is an open, human- and agent-friendly format for representing
*knowledge*: the metadata, context, and curated insight that surrounds
data and systems. It is designed to be authored by people, generated by
agents, exchanged across organizations, and consumed by both.

The format is intentionally minimal: a directory of markdown files with
YAML frontmatter. There is no schema registry, no central authority, and
no required tooling. If you can `cat` a file, you can read OKF; if you
can `git clone` a repo, you can ship it.

This document is self-contained: it specifies everything needed to
produce and consume OKF v0.2. A summary of what changed from v0.1 is in
§13.

### Conformance & Keyword Definitions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
"SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
"OPTIONAL" in this document are to be interpreted as described in BCP 14
[RFC2119] [RFC8174] when, and only when, they appear in all capitals, as
shown here.

# Part I — Core Open Knowledge Format (OKF)

Chapters 1–13 define core OKF: a minimal, tool-free markdown container
for human and agent knowledge representation.

## 1. Motivation

The space of knowledge representation for AI agents is evolving quickly,
and many incompatible conventions are emerging. OKF takes the position
that knowledge is best represented in commonly accessible, established
formats that are:

- **Readable** by humans without tooling.
- **Parseable** by agents without bespoke SDKs.
- **Diffable** in version control.
- **Portable** across tools, organizations, and time.

Increasingly, a knowledge corpus is not authored once and then read: it
is **continuously written and maintained by agents**. When most concepts 
are machine-generated, a consumer needs answers that a plain 
markdown-plus-frontmatter convention does not make first-class:

1. What was this created from, and how was it verified? (**provenance**)
2. How much should I trust it? (**trust**)
3. Is it still true? (**freshness**)
4. Is it the current version? (**lifecycle**)
5. Was this number produced the way we said it must be? (**attestation**)

OKF v0.2 makes provenance, trust, lifecycle, and attestation first-class
while keeping the format minimally opinionated. The format is minimally 
opinionated. It standardizes only the small set of structural conventions 
needed to make a knowledge corpus self-describing — anything beyond that
is left to the producer.

### Goals

1. Define a universal format that **producers** (people, agents, export
   pipelines) can write into.
2. Inform how **consumers** (agents, UIs, search indexes, deterministic
   code) should read and traverse it.
3. Facilitate **exchange** of knowledge across systems and organizations.
4. Standardize the small set of frontmatter fields that make an
   agent-maintained corpus **trustable**, without prescribing any runtime.

### Non-goals

- Defining a fixed taxonomy of concept types.
- Prescribing storage, serving, or query infrastructure.
- Replacing domain-specific schemas (Avro, Protobuf, OpenAPI, and so on).
  OKF *references* them; it does not subsume them.
- Specifying a packaging or invocation standard for the code an executor
  or attester points at. OKF fixes the interface, not the packaging.

These non-goals apply to core OKF. The optional ODKF profile (Part II)
adds deployment requirements for implementations that claim profile
conformance; they do not apply to a core OKF bundle.

## 2. Terminology

- **Knowledge Bundle** (or **bundle**): A self-contained, hierarchical
  collection of knowledge documents. The unit of distribution.
- **Concept**: A single unit of knowledge within a bundle, represented as
  one markdown document. It may describe a tangible asset (a table, an
  API), an abstract idea (a metric, a business process), or anything in
  between.
- **Concept ID**: The path of the concept's file within the bundle, with
  the `.md` suffix removed.
- **Frontmatter**: A YAML metadata block delimited by `---` at the top of
  a markdown file.
- **Body**: Everything in the file after the frontmatter.
- **Link**: A standard markdown link from one concept to another, used to
  express relationships beyond the implicit parent/child hierarchy.
- **Source**: A material a concept derives from, external or internal to
  the bundle, recorded in the `sources` frontmatter field.
- **Provenance**: The set of sources a concept derives from.
- **Credibility signal**: An objective, per-source fact (`author`,
  `usage_count`, `last_modified`) used to infer trust; OKF records the
  signals, not a verdict (see §5.1).
- **Actor**: A string identifying who or what performed an action, using
  the convention `<producer>/<version>` for agents, `human:<id>` for
  people, and `process:<id>` for automated processes (see §7).
- **Trust tier**: A level derived from a concept's `verified` field:
  unverified, machine-confirmed, or human-reviewed (see §5.3).
- **Attested Computation**: A concept (`type: Attested Computation`)
  carrying a sanctioned way to compute a value, so a consumer can confirm
  the value was produced by running it (see §10).
- **Executor**: Run instructions or code that executes a computation and
  returns a receipt (see §10.2).
- **Receipt**: The evidence a run returns, shaped by `executor.receipt`; a
  runtime artifact, not stored in the bundle (see §10).
- **Attester**: Deterministic (no-LLM) code that inspects a receipt and
  returns a verdict (see §10.2).

## 3. Bundle structure

A bundle is a directory tree of markdown files. The directory structure
is independent of the domain: producers organize concepts however makes
sense for the knowledge being captured.

```text
path/to/bundle/
  index.md                      # Optional. Directory listing for progressive disclosure.
  log.md                        # Optional. Chronological history of updates.
  <concept>.md                  # A concept at the bundle root.
  <subdirectory>/               # Subdirectories organize concepts into groups.
    index.md
    <concept>.md
    <subdirectory>/
      ...
```

A bundle MAY be distributed as:

- A git repository (recommended, since it provides history, attribution,
  and diffs).
- A tarball or zip archive of the directory.
- A subdirectory within a larger repository.

### 3.1 Reserved filenames

The following filenames have defined meaning at any level of the
hierarchy and MUST NOT be used for concept documents:

| Filename   | Purpose                          |
|------------|----------------------------------|
| `index.md` | Directory listing. See §8.       |
| `log.md`   | Update history. See §9.          |

All other `.md` files are concept documents.

Tags remain a first-class concept through the `tags` frontmatter field
(§4.1). OKF does not specify a separate file format for aggregating
documents by tag; a consumer that wants a tag-browsing view can
synthesize one at consumption time by scanning frontmatter.

## 4. Concept documents

Every concept is a UTF-8 markdown file with two parts:

1. A **YAML frontmatter block**, delimited by `---` on its own line at the
   start of the file and a closing `---` on its own line.
2. A **markdown body**, containing free-form content.

### 4.1 Frontmatter

```yaml
---
type: <Type name>                  # REQUIRED
title: <Optional display name>
description: <Optional one-line summary>
resource: <Optional canonical URI for the underlying asset>
license: <Optional SPDX identifier or license URL>
tags: [<tag>, <tag>, ...]          # Optional
# ... trust, lifecycle, provenance, and computation families (see §5, §10)
# ... other producer-defined key/value pairs
---
```

**Required:**

- `type`: A short string identifying the kind of concept. Consumers use it
  for routing, filtering, and presentation. Example values:
  `BigQuery Table`, `BigQuery Dataset`, `API Endpoint`, `Metric`,
  `Playbook`, `Reference`, `Attested Computation`.

  Type values are **not** registered centrally. Producers SHOULD pick
  values that are descriptive and self-explanatory; consumers MUST
  tolerate unknown types gracefully, typically by treating them as generic
  concepts.

`type` is the only always-required key; a concept carrying just `type` is
fully conformant (§11).

**Recommended:**

- `title`: Human-readable display name. If omitted, consumers MAY derive a
  title from the filename.
- `description`: A single sentence summarizing the concept. Used by
  `index.md` generators, search snippets, and previews.
- `resource`: A URI that uniquely identifies the underlying asset the
  concept describes. Absent for concepts that describe abstract ideas
  rather than physical resources.
- `license`: A standard license identifier (SPDX or a URL), for example
  `CC-BY-4.0`, so reuse rights are machine- and human-readable.
- `tags`: A YAML list of short strings for cross-cutting categorization.

The optional **provenance**, **trust**, and **lifecycle** families (§5) and
the **computation** fields for Attested Computation concepts (§10) may also
appear.

**Extensions:** Producers MAY include any additional keys. Consumers
SHOULD preserve unknown keys when round-tripping and MUST NOT reject
documents with unrecognized fields.

### 4.2 Body: The Human-AI Operational Interface

The body is standard UTF-8 markdown. In OKF/ODKF v0.2, the body is not mere ancillary text; it is the **primary cognitive and operational interface between humans and AI agents**. While the YAML frontmatter and referenced contracts define machine-executable syntactic schemas (Frictionless, Parquet, DuckDB), the markdown body provides the necessary domain semantics, methodological context, and operational instructions for tools and agents:

1. **Context Engineering for LLM Agents:** Structural elements (headings, bullet points, fenced code blocks, and markdown tables) provide agents with high-density, token-efficient context, preventing hallucination during query synthesis.
2. **Operational Tool Interaction:** Documents SHOULD include fenced code blocks with executable SQL queries, API calls, or MCP tool invocations demonstrating how downstream engines (e.g. `datamesh_sql_query`) resolve the underlying physical data.
3. **Methodological Context & Biases:** Qualitative warnings, sampling frames, statistical coverage, and regulatory constraints (Habeas Data / zero-microdata rules).

The following headings have **conventional** normative meaning:

| Heading | Purpose | Target Consumer |
| :--- | :--- | :--- |
| `## Description & Domain Context` | Human and AI prose describing the purpose and relevance of the asset. | Human / Agent |
| `## Methodology, Scope & Biases` | Sampling frame, statistical limitations, and data quality caveats. | Auditor / Researcher / Agent |
| `## Operational Interaction & Example Queries` | Ready-to-execute fenced SQL (`SELECT ...`), CLI commands, or MCP calls. | Agent Tooling / Analyst |
| `## Data Dictionary & Semantic Anchors` | Structured mapping of column attributes, units of measure, and SKOS URIs. | Human / Machine |
| `# Computation` (or `## Computation & Verification`) | The sanctioned computation of an Attested Computation. See §10. | Runtime / Verifier |

Per-claim attribution to external sources uses markdown footnotes keyed to
`sources` entries rather than a body citations list (§5.1).

### 4.3 Example: a concept bound to a resource

```markdown
---
type: BigQuery Table
title: Customer Orders
description: One row per completed customer order across all channels.
resource: https://console.cloud.google.com/bigquery?p=acme&d=sales&t=orders
tags: [sales, orders, revenue]
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-05-28T14:30:00Z }
---

# Schema

| Column        | Type      | Description                              |
|---------------|-----------|------------------------------------------|
| `order_id`    | STRING    | Globally unique order identifier.        |
| `customer_id` | STRING    | Foreign key into [customers](/tables/customers.md). |
| `total_usd`   | NUMERIC   | Order total in US dollars.               |
| `placed_at`   | TIMESTAMP | When the customer submitted the order.   |

# Joins

Joined with [customers](/tables/customers.md) on `customer_id`.
```

### 4.4 Example: a concept not bound to a resource

```markdown
---
type: Playbook
title: "Incident response: data freshness alert"
description: Steps to triage a freshness alert on the orders pipeline.
tags: [oncall, incident]
generated: { by: human:ahormati, at: 2026-04-12T09:00:00Z }
---

# Trigger

A freshness alert fires when `orders` lags more than 30 minutes behind its
expected SLA. See the [orders table](/tables/orders.md).

# Steps

1. Check the [ingestion job dashboard](https://example.com/dash).
2. ...
```

## 5. Provenance, trust, and lifecycle

These frontmatter families make "where did this come from," "how much
should I trust it," and "is it still current" answerable from frontmatter.
All are optional. Their absence carries meaning: an unverified concept is
distinguishable from a verified one, but is never rejected (§11).

Every timestamp-valued key in OKF is an ISO 8601 datetime with an explicit
UTC offset, for example `2026-06-30T14:00:00Z`.

### 5.1 Provenance: `sources`

`sources` records the materials a concept derives from, external or
internal to the bundle.

```yaml
sources:
  - id: ga4-schema
    resource: https://developers.google.com/analytics/bigquery/export-schema
    title: GA4 BigQuery Export schema
    author: team:ga4-docs
    usage_count: 5000
    last_modified: 2026-05-30T00:00:00Z
usage_window: { from: 2026-06-01T00:00:00Z, to: 2026-06-30T00:00:00Z }
```

Each `sources` entry:

- `resource`: REQUIRED within an entry. Names either a concrete artifact a
  consumer can follow (an absolute URL, a bundle-relative path, or a path
  into a `references/` subdirectory, §6) or a population or scope descriptor
  it cannot (for example `all queries in BigQuery project X`).
- `id`: Optional. A stable key used to attribute individual claims (see
  below). SHOULD be present when the body cites the source.
- `title`: Optional. Human-readable label for the source.
- The optional credibility signals `author`, `usage_count`, and
  `last_modified`, described next.

**Source credibility signals.** OKF records objective, per-source signals
so a consumer can judge how much to trust a concept by judging the sources
it was extracted from. It does not store a credibility score: a score is
subjective, unportable across consumers, and goes stale. Credibility is
*inferred* from the signals, the same way trust tiers are (§5.3), not
stored. Each signal is optional and lives on a `sources` entry:

- `author`: Who or what produced the source, in the actor convention (§7).
  An authority signal.
- `usage_count`: How often `resource` was exercised (dashboard views, query
  executions, page reads) over `usage_window`. An adoption and liveness
  signal. For a single artifact it is that artifact's own exercise count;
  for a scope descriptor it is the number of exercises within the scope that
  touch the concept.
- `last_modified`: When the source itself last changed. A recency signal,
  distinct from `generated.at` (§5.2), which records when the concept was
  written.
- `usage_window`: Written once as a sibling of `sources`, it frames every
  `usage_count` with a `{ from, to }` datetime range. A single entry MAY
  carry its own `usage_window` to override the shared one.

`usage_count` is a coarse signal. It is comparable at the
alive-versus-dead and order-of-magnitude level, and against a source's own
history over time, but not as a precise cross-kind ranking: a scheduled
query's executions and a human's deliberate dashboard views do not carry
equal weight. Consumers SHOULD read it as liveness and trend, not as a
score.

Lineage is expressed through links, not a dedicated field. When a
`resource` points at another OKF concept, the derivation edge already
exists in the bundle graph (§6), so a consumer MAY recurse into that
source's own `sources` and let credibility propagate. External leaf sources
carry only their intrinsic signals. Deeper lineage (an explicit external
`derived_from`, or data lineage) is out of scope for core OKF v0.2; the
ODKF profile defines runtime lineage in §17.

**Per-claim attribution.** To attribute a specific claim, use a markdown
footnote whose label is a `sources[].id`:

```markdown
The `events_` table is sharded daily as `events_YYYYMMDD`.[^ga4-schema]

[^ga4-schema]: GA4 BigQuery Export schema
```

The footnote label is the join key into `sources`; consumers resolve
attribution through the matching entry, not by parsing the footnote prose.
Labels are keyed rather than positional (`sources[0]`) because agents
constantly rewrite these documents: a positional index misattributes
silently the moment the list is reordered, whereas a stable `id` survives
reordering.

### 5.2 Trust: `generated` and `verified`

`generated` records how the current content was produced. `verified`
records who or what has confirmed the content against its sources or
`resource`. They are kept distinct because who *wrote* a concept need not
be who *confirmed* it.

```yaml
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
```

- `generated.by`: REQUIRED within `generated`. An actor (§7).
- `generated.at`: An ISO 8601 datetime marking the content's last
  meaningful change. Consumers use it to tell a recent edit from a stale
  fact.

```yaml
verified:
  - { by: human:ahormati, at: 2026-06-25T09:00:00Z }
  - { by: process:finance-nightly, at: 2026-06-26T02:00:00Z }
```

- `verified`: A list of verification events, each with `by` (an actor) and
  `at` (an ISO 8601 datetime). Multiple entries capture independent
  checks, for example a human sign-off plus a nightly process. "How
  recently" is the latest `at`.
- `verified` is independent of `generated.at`: content can change without
  re-confirmation, and facts can be re-confirmed without regeneration.
- A single verifier MAY be written as one `{ by, at }` mapping without the
  list dash. Consumers MUST treat a bare mapping as a one-element list:

```yaml
verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }
```

### 5.3 Trust tiers

Consumers derive a trust tier from `verified`, lowest to highest:

- No `verified` key ⇒ **unverified**.
- `verified` by non-`human:` actors only ⇒ **machine-confirmed**.
- `verified` by a `human:<id>` actor ⇒ **human-reviewed**.

A concept with no trust frontmatter is still consumable; consumers MUST
NOT reject it (§11). Trust tiers are advisory signals, not access control.

### 5.4 Lifecycle: `status`

```yaml
status: stable        # recommended: draft | stable | deprecated
```

- `draft`: not yet reviewed; possibly incomplete.
- `stable`: default; ready for consumption.
- `deprecated`: kept for links and history; no longer current.

Absent `status` ⇒ `stable`. The vocabulary is open: producers MAY use
additional lifecycle values (for example `proposed`, `active`, `retired`,
or `superseded`), and consumers MUST treat unknown values as advisory
rather than rejecting the concept. A `superseded` concept SHOULD also
carry `superseded_by` pointing at its replacement.

### 5.5 Lifecycle: `stale_after`

```yaml
stale_after: 2026-09-23T00:00:00Z   # content is stale on/after this instant
```

Optional. An absolute instant. A concept is stale when
`now >= stale_after`. An absolute instant, not a relative TTL, keeps the
staleness decision a plain comparison with no reference to when the
concept was read.

For backward compatibility, consumers MAY also accept a legacy
`freshness: { cadence, expires }` mapping; `expires` is equivalent to
`stale_after`, and `cadence` is advisory.

## 6. Cross-linking and paths

### 6.1 Links between concepts

Concepts MAY link to other concepts using standard markdown links. Two
forms are supported:

- **Absolute (bundle-relative):** begins with `/`, interpreted relative to
  the bundle root. This is the **recommended** form because it is stable
  when documents are moved within their subdirectory.

  ```markdown
  See the [customers table](/tables/customers.md) for the join key.
  ```

- **Relative:** a standard markdown relative path.

  ```markdown
  See the [neighboring concept](./other.md).
  ```

A link from concept A to concept B asserts a *relationship*. The specific
kind (parent/child, references, joins-with, depends-on) is conveyed by the
surrounding prose, not by the link itself. Consumers that build a graph
view typically treat all links as directed edges of an untyped
relationship.

Consumers MUST tolerate broken links: a link whose target does not exist
in the bundle is not malformed; it may simply represent not-yet-written
knowledge.

### 6.2 Path-valued fields

Several fields name a path or URI: `resource`, `sources[].resource`,
`computation`, `executor.resource`, and `attester.resource` (§10). A
`sources[].resource` may instead be a scope descriptor (§5.1), in which
case it is not a path. Each path-valued field accepts:

- an absolute URL (for example `https://...`),
- a bundle-relative path beginning with `/`, or
- a relative path (for example `../computations/revenue.md`).

### 6.3 The `references/` convention

A `references/` subdirectory conventionally mirrors external material, run
instructions, or code as first-class concepts within the bundle. Sources,
executors, and attesters commonly point into it (for example
`references/attesters/revenue.py`). It is a naming convention, not a
requirement.

## 7. Actor convention

Fields that record an identity (`generated.by`, `verified[].by`) use a
single actor convention:

- `<producer>/<version>` for agents and tools, for example
  `reference_agent/gemini-2.5-pro`.
- `human:<id>` for a person, for example `human:ahormati`.
- `process:<id>` for an automated process, for example
  `process:finance-nightly`.

Consumers that classify trust (§5.3) key off the `human:` prefix in Level 0
for descriptive human provenance. In Level 1 and Level 2 profiles (§11, §14.5),
elevated trust tiers (`verified`, `official`) MUST NOT rely on string prefixes
alone and require verifiable cryptographic signatures (`did:github:<username>`,
OpenSSH `ssh-ed25519` key fingerprints, or Ed25519 signatures declared in
`signatures[]`).

## 8. Index files

An `index.md` file MAY appear in any directory, including the bundle root.
It enumerates the directory's contents to support **progressive
disclosure**: letting a human or agent see what is available before
opening individual documents.

Index files contain no frontmatter, with one exception: a bundle-root
`index.md` MAY carry an `okf_version` key (§12). The body uses one or more
sections, each grouping concepts under a heading:

```markdown
# Section / Group Heading

* [Title 1](relative-url-1) - short description of item 1
* [Title 2](relative-url-2) - short description of item 2

# Another Section

* [Subdirectory](subdir/) - short description of the subdirectory
```

Entries SHOULD include the description from the linked concept's
frontmatter. Producers MAY generate `index.md` automatically; consumers
MAY synthesize one on the fly when none is present.

---

## 9. Log files

A `log.md` file MAY appear at any level of the hierarchy to record the
history of changes to that scope. The format is a flat list of
date-grouped entries, newest first:

```markdown
# Directory Update Log

## 2026-05-22
* **Update**: Added a BigQuery table reference for [Customer Metrics](/tables/customer-metrics.md).
* **Creation**: Established the [Dataplex Playbook](/playbooks/dataplex.md).

## 2026-05-15
* **Initialization**: Created foundational directory structure.
```

Date headings MUST use ISO 8601 `YYYY-MM-DD` form. Log entries are prose;
the leading bold word (`**Update**`, `**Creation**`, `**Deprecation**`) is
a convention, not a requirement.

## 10. Attested computations concept

An Attested Computation concept carries not just what a value *means* but a
sanctioned way to *compute* it, so a consumer can confirm the agent ran the
blessed computation instead of improvising its own. Provenance (§5.1)
answers "where did this claim come from"; attestation answers "was this
number produced the way we said it must be." OKF records the computation
and the means to check it; it does not execute anything itself.

### 10.1 A computation is its own concept

A sanctioned computation is a standalone concept of
`type: Attested Computation`. A concept that needs the value (a `Metric`, a
`BigQuery Table`) links to it with a normal markdown link (§6). Three
properties motivate the standalone concept:

- **`runtime` defines what `parameters` mean.** A parameter is a SQL bind
  variable, a dbt var, or a Python argument depending on the runtime.
  Keeping `runtime` and `parameters` in one frontmatter makes the binding
  semantics self-evident.
- **One computation, many consumers.** The same computation can back a
  metric, a dashboard concept, and a report; as a concept it is referenced
  once and reused.
- **Trust state is per computation.** `verified`, `stale_after`, and a
  single `attester` describe one thing. Revenue, profit, and margin each
  verify and attest independently, which is three concepts, not three
  entries in one frontmatter.

### 10.2 Contract fields

The contract is the concept's top-level frontmatter. In addition to the
provenance, trust, and lifecycle families (§5), an Attested Computation
concept carries:

- `runtime`: REQUIRED for this type. The single field that says how to run
  the computation, and so how the executor and attester interpret it and
  what `parameters` mean. Example values: `bigquery`, `postgres`, `dbt`,
  `python`, `Looker`.
- `parameters`: A list of the typed, named holes the agent may fill. Each
  entry: `{ name, type, required }`. Binding semantics follow `runtime`.
- `computation`: Optional. A path (§6.2) to a file holding the
  computation, used instead of an inline body fence (see §10.3). Absent ⇒
  the body `# Computation` fence is the computation.
- `executor`: How the computation is run. `resource` names run
  instructions or code; a runner (an agent, or deterministic consumer
  code) follows it. `receipt` declares the fields a run must return, the
  evidence the attester inspects (for example a BigQuery `job_id` and the
  SQL the job actually executed).
- `attester`: The deterministic check. `resource` names code (no LLM) that
  takes a receipt and returns a verdict. It is meant to run consumer-side.
  
  **Attester Sandboxing Invariant (Security):** Because an `attester.resource`
  may originate from an untrusted third-party bundle, conforming consumers
  MUST NOT execute external attester scripts directly on the host system
  without process isolation. Runtimes MUST execute attester code within a
  sandboxed execution environment (such as a WebAssembly / WASI runtime with
  zero host filesystem/network access, or an unprivileged, isolated container
  with bounded CPU and memory limits), or verify execution through declarative
  receipt comparison (e.g. AST SQL equality).

What sits behind a `resource` (a Skill, a script, a container) is a
packaging choice; OKF fixes the interface, not the packaging (§1).

```markdown
---
type: Attested Computation
title: Revenue for fiscal year
description: Recognized revenue for a fiscal year, per Finance's definition.
status: stable
runtime: bigquery
parameters:
  - { name: year, type: integer, required: true }
executor:
  resource: references/skills/run-on-bq.md
  receipt: [job_id, executed_sql, result]
attester:
  resource: references/attesters/revenue.py
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }
stale_after: 2026-09-23T00:00:00Z
sources:
  - id: rev-policy
    resource: https://wiki.acme/finance/revenue-recognition
    title: Revenue recognition policy
---

# Computation

```sql
SELECT SUM(amount) AS revenue
FROM finance.recognized_revenue
WHERE fiscal_year = @year
```

The computation binds only the declared `parameters`, per the recognition
policy.[^rev-policy]

[^rev-policy]: Revenue recognition policy
```

### 10.3 The computation

Provide the computation in one of two ways:

- **Inline:** a single fenced code block in the body under `# Computation`.
  Best for a short computation reviewed alongside the contract.
- **File:** set `computation` to a path (§6.2) and omit the body fence.
  Best for a long or generated computation, or one already kept as a real
  file shared with non-OKF tooling.

```yaml
runtime: bigquery
computation: references/computations/lib/revenue.sql
parameters:
  - { name: year, type: integer, required: true }
```

The agent MAY only supply *values* for the declared `parameters`; it MUST
NOT author or edit the computation. Binding `computation` with the
parameter values into the executable artifact is the consumer's job, and
the attester independently re-derives that same binding to compare against
what actually ran. Because the comparison is on the expanded, compiled
artifact the receipt carries (`executed_sql`, `compiled_sql`), a rewritten
query, a swapped computation file, or a mutated dependency fails the check.
A typed, parameter-only surface is what makes "did the sanctioned thing
run" a mechanical comparison rather than a judgement call.

### 10.4 Concepts that use a computation

A document is rarely a single computation. An income-statement overview
that discusses revenue, profit, and margin stays one readable concept and
links to one Attested Computation per figure:

```markdown
---
type: Metric
title: Revenue
description: Recognized revenue for a fiscal year.
tags: [finance, revenue]
status: stable
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
---

# Definition

Recognized revenue sums `amount` over rows booked to the fiscal year,
computed by [the revenue computation](../computations/revenue.md).
```

Because each computation is its own concept, revenue can be fresh while
profit is past its `stale_after`, and each attests on its own run.
Co-locating them is a directory choice (a `computations/` folder with an
`index.md`), not a frontmatter one.

### 10.5 How a consumer uses it (informative)

This subsection is informative, not normative. The runtime artifacts below
are **not** stored in the bundle.

1. **Discover** via `type: Attested Computation`, a frontmatter signal
   liftable into `index.md`; a consumer reaches one directly or by
   following a link from a concept that uses it.
2. **Load** the contract from frontmatter and the computation from the
   body (or the file named by `computation`).
3. **Parameterize**: the agent supplies values for the declared parameters.
4. **Execute**: the executor runs the bound computation and returns a
   receipt shaped by `executor.receipt`.
5. **Attest**: the consumer runs the attester over the receipt. It
   confirms provenance (the computation that ran equals `computation` bound
   with the claimed parameters, not agent-authored SQL) and fidelity (the
   displayed value matches the receipt's authoritative source, re-read by
   job id rather than taken from the agent's text).
6. **Gate**: refuse to display a failing attestation; warn or refuse when
   `now >= stale_after`. On success, surface the verdict (for example a
   link to the job log) so trust is visible.

### 10.6 Verification versus attestation

`verified` (§5.2) and attestation are distinct, and both exist:

- `verified` confirms the *definition* still matches policy. It is
  doc-level, slow, and recorded in the bundle.
- Attestation confirms a single *run* produced the value the sanctioned
  way. It is per-call, runtime, and not stored in the bundle.

A concept with a stale definition can still attest cleanly, and a
freshly-verified definition still requires attestation on each run, which
is why both are needed.

## 11. Conformance & Modular Profiles (W3C QA SpecGL)

In accordance with the **W3C Quality Assurance Framework: Specification Guidelines (SpecGL)** and **IETF RFC 2119 / RFC 8174**, OKF/ODKF v0.2 defines three cumulative **Conformance Profiles** (Dimensions of Variability) so lightweight tools can adopt the core format without implementing distributed P2P networking:

1. **Level 0 — Core Knowledge Bundle (`level-0-core`):** Markdown + YAML frontmatter (`type`), cross-links, `index.md`, `log.md`, `sources`, `generated`, `verified`, `status`, and `stale_after` (Chapters 1–13).
2. **Level 1 — Data Product & Contracts Profile (`level-1-contracts`):** Includes Level 0 plus `contracts` (Frictionless/DCAT/OpenAPI/CWL), canonical triads (`catalog:dataset:resource`), `skos` anchors, physical units (**UCUM/QUDT** `unit` and `aggregation_behavior`), semantic schema evolution (`okf diff`), `Attested Computation` verification (`okf attest`), and `zero_microdata` governance with *k-anonymity* (`min_group_size`).
3. **Level 2 — Sovereign Federated / P2P Profile (`level-2-sovereign`):** Includes Level 1 plus `okf://` and `<dataset>.<resource>@<catalog>` Sovereign DNS resolution, composite archive `#fragment` extraction (RFC 7233 HTTP Range), Ed25519/OpenSSH cryptographic signatures, and Kademlia DHT / GossipSub transport (§15).

A bundle is **conformant** with OKF v0.2 (`level-0-core`) if:

1. Every non-reserved `.md` file in the tree contains a parseable YAML
   frontmatter block.
2. Every frontmatter block contains a non-empty `type` field.
3. Every reserved filename (`index.md`, `log.md`) follows the structure in
   §8 and §9 respectively when present. In single-dataset ODKF nodes (`level-1-contracts`), a root `index.md` MAY act as the primary Root Concept Manifest when it declares an explicit `type` (e.g., `dcat:Dataset`, `dcat:DataService`, or `dcat:CatalogRecord`).

A bundle or dataset is **conformant with Level 1 (`level-1-contracts`)** if:

1. It satisfies all Level 0 requirements.
2. Every declared contract in `contracts[]` resolves to a valid local path (`path`) or reachable URI (`ref`).
3. Every resource reference conforms to the Canonical Triad grammar (§14.4).
4. If `type == dataset`, ontological anchors in `skos` are valid HTTP/HTTPS URIs.
5. All validation rules `RULE-01` through `RULE-12` (§14.5) pass with zero `ERROR` issues.

A node or catalog deployment is **conformant with Level 2 (`level-2-sovereign`)** if:

1. It satisfies all Level 1 requirements.
2. Every digital signature declared in `signatures[]` verifies cryptographically against the publisher's public key or verified identity (`did:github`, OpenSSH `ssh-ed25519`).
3. Sovereign resource addresses resolve across federated registries (§14.4) or P2P transports ([RFC 0001](docs/rfcs/0001-p2p-sovereign-network.md)).

When the trust, lifecycle, provenance, or computation families are
present, producers SHOULD follow §5 through §10, and consumers:

- MUST treat a bare `verified` mapping as a one-element list (§5.2).
- MUST NOT reject a concept for missing any optional family (§5.3).
- SHOULD derive trust tiers and staleness only from the fields specified
  here, and SHOULD surface, not silently drop, a failing attestation
  (§10.5).

Consumers SHOULD treat all other constraints as soft guidance. In
particular, consumers MUST NOT reject a bundle because of:

- Missing optional frontmatter fields.
- Unknown `type` values.
- Unknown additional frontmatter keys.
- Broken cross-links.
- Missing `index.md` files.

## 12. Versioning

This document specifies OKF version **0.2**. Revisions are versioned as
`<major>.<minor>`:

- A **minor** version bump introduces backward-compatible additions (new
  optional fields, new conventional section headings).
- A **major** version bump may make breaking changes (renaming required
  fields, changing reserved filenames).

Bundles MAY declare the version they target with `okf_version: "0.2"` in a
bundle-root `index.md` frontmatter block (the only place frontmatter is
permitted in an `index.md`). Consumers that do not understand the declared
version SHOULD attempt best-effort consumption rather than refusing the
bundle.

### 12.1 Standardized `AttestationVerdict` Wire Format (`okf attest`)

To enable deterministic verification (`okf attest <concept.md> --receipt <json_or_path>` or `--sql <query>`), any conforming attester MUST emit a JSON object over `stdout` adhering to the following contract:

```json
{
  "verdict": "verified | refuted | error",
  "canonical_query_hash": "sha256:...",
  "checked_at": "2026-11-05T12:00:00Z",
  "reason": "AST/Canonical SQL match & parameter binding verified against sanctioned computation"
}
```

### 12.2 Semantic Schema Evolution (`okf diff`)

When evolving bundles or `datapackage` contracts across versions (`supersedes` / `superseded_by`), `okf diff <bundle_v1> <bundle_v2>` classifies modifications according to **Semantic Versioning 2.0.0**:
- **PATCH:** Documentation or prose corrections in the Markdown body without schema alterations.
- **MINOR:** Backward-compatible additions (new optional columns, new resources, or new concept nodes).
- **MAJOR (Breaking):** Removal or renaming of columns/resources, data type mutations, or changes to physical units (**UCUM/QUDT**) or ontological anchors (`rdfType` / `skos`).

### 12.3 Considered and Deferred

The following are intentionally left to a future revision:

- The standardized attester sandboxing ABI and remote attestation caching.
- Semantic-layer templates (Looker, dbt) where the attester comparison
  shifts from SQL equality to model-and-binding equality.

## 13. Changes from v0.1

v0.2 supersedes OKF v0.1 and is a minor version bump under §12, except for
two deliberate breaking changes called out below because they rename or
retire v0.1 fields. A v0.1 bundle is consumable by a v0.2 consumer under
the fallbacks noted here.

### 13.1 Breaking changes

- **`timestamp` is superseded by `generated.at`.** A concept's last
  content change is now recorded as `generated: { by, at }` (§5.2).
  Consumers MAY fall back to a legacy `timestamp` when `generated` is
  absent.
- **The body `# Citations` list is superseded by `sources`.** Provenance
  moves to frontmatter (§5.1). Consumers SHOULD read `sources` and MAY
  still parse a legacy `# Citations` body list for v0.1 documents.

### 13.2 Additive changes

All of the following are additive: new optional keys, one new concept
type, and one new conventional heading. Their absence yields a plain v0.1
concept.

- New frontmatter families: `sources` with its per-source credibility
  signals (`author`, `usage_count`, `last_modified`) and the `usage_window`
  sibling; `generated`, `verified`; `status`, `stale_after` (§5).
- New concept type `Attested Computation` and its computation keys
  `runtime`, `parameters`, `computation`, `executor`, `attester` (§10).
- New conventional body heading `# Computation` (§4.2).
- The actor convention for `generated.by` and `verified[].by` (§7).

Everything else (bundle structure, reserved filenames, the required
`type`, recommended `title`/`description`/`resource`/`tags`, cross-linking,
index files, log files, permissive conformance) is carried forward
unchanged.

# Part II — The ODKF v0.2 Profile

Chapters 1–13 define core OKF: a minimal, tool-free markdown container.
This part defines **ODKF v0.2** (Open Data Knowledge Format), an optional
profile for sovereign, federated data ecosystems. Profile requirements
apply only to implementations that claim ODKF conformance; a core OKF
bundle remains conformant under §11 without implementing them. ODKF v0.2
tracks OKF v0.2 and follows the same versioning rules (§12).

## 14. Open Data Knowledge Format (ODKF v0.2) Extension: Meta-Standard Index & Tripartite Epistemology

ODKF is a profile of OKF v0.2 for sovereign data-mesh architectures,
federated analytical catalogs, and verifiable data products. Rather than
competing with existing standards or forcing centralized conversions, it
acts as a **meta-standard and index of indexes** that references external
formats without duplicating data.

### 14.1 Foundational Architecture Principles

1. **Meta-Standard Index ("Index of Indexes"):** OKF acts as the lightweight, human-and-AI-friendly orchestrator (Markdown + YAML frontmatter). It does not duplicate schemas; it catalogs, links, and indexes domain-specific standards (**W3C DCAT v3**, **Frictionless DataPackage**, **OpenAPI 3.1**, **CWL**, **Schema.org**).
2. **By-Reference Resolution (`ref:` Clause):** To maintain the **Single Source of Truth (SSOT)** and eliminate information redundancy, contracts, schemas, and pipelines can be referenced directly via `ref:` (remote URL) or `path:` (local path). Downstream runtimes and validators resolve and cache external schemas on demand.
3. **Tripartite Epistemological Separation (Metadata vs Paradata vs Data):**
   - **Metadata (Descriptive & Conceptual):** Defines *what* the knowledge asset represents (domain, titles, dimensions, ontological anchors in SKOS/Wikidata, syntactic contract references).
   - **Paradata (Methodological & Process Context):** Captures *how* the asset was produced, verified, and evolved (creation actor `generated.by`, verification chain `verified[]`, lifecycle `status` / `stale_after`, and cryptographic lineage `lineage.transformations`).
   - **Data (Substantive Payload):** The actual underlying content (tuples, matrices, arrays, columnar Parquet partitions, embeddings, or dynamic API streams).
4. **Operational Resource Taxonomy (Orthogonal Matrix):**
   - **By Dynamism:**
     - *Static Resources:* Immutable, content-addressed files (CSV, Parquet, GeoJSON, SQLite, DuckDB, nested ZIP/TAR archives accessible via zero-copy range requests).
     - *Dynamic Resources:* Continuously flowing or queryable endpoints (REST/GraphQL APIs, Apache Arrow Flight SQL streams, federated live SQL views).
   - **By Locality:**
     - *Local Resources:* Residing on host filesystem or within packaged bundle.
     - *Remote Resources:* Hosted across distributed infrastructures (HTTP/S, S3/MinIO buckets, sovereign P2P networks, or CKAN portals).
5. **Extensible Plugin/Connector Architecture:** The format defines declarative ports, enabling third-party plugins to harvest, translate, and query diverse backend standards seamlessly.
6. **Zero-Microdata by Design:** Public knowledge nodes and catalogs publish documentation, schemas, dimensions, and contracts. Heavy physical data resides externally or behind access controls. Non-authenticated queries are restricted to aggregate statistics (`COUNT`, `SUM`, `AVG`, `GROUP BY`).

### 14.2 Frontmatter Specification for ODKF Concepts

In addition to core OKF fields, an ODKF concept document (`type: dataset`, `service`, `indicator`, `catalog`, or `playbook`) supports the following normative fields. ODKF uses lowercase profile type names; core OKF keeps type values unregistered, so consumers MUST tolerate both styles (§4.1).

```yaml
---
# --- Core OKF Fields (§4.1) ---

description: Official voting statistics # RECOMMENDED. Single-line summary

tags: [demography, elections, census]  # OPTIONAL. Categorization tags
generated: { by: process:ine-export, at: 2026-05-01T00:00:00Z }

# --- Semantic Anchors (ODKF v0.2) ---

  - http://www.wikidata.org/entity/Q39825    # Census / Election
  - https://schema.org/GovernmentData

dimensions:                            # OPTIONAL. Analytical dimensions for OLAP slicing
  - departamento
  - municipio
  - año

# --- Syntactic Contracts (ODKF v0.2) ---
contracts:                             # REQUIRED for active data and service concepts
  - type: datapackage                  # Frictionless DataPackage / Table Schema
    path: datapackage.yaml
  - type: openapi                      # REST API endpoints (OpenAPI v3 / Springdoc)
    path: https://api.gob.bo/v3/api-docs
  - type: cwl                          # Executable batch tasks / pipelines
    path: tasks/clean_data.cwl

# --- Lineage & Cryptographic Integrity (ODKF v0.2) ---
lineage:
  source:
    - url: https://raw.source.gob.bo/censo_raw.csv
  transformations:
    - tool: scripts/clean_data.py
      type: script
      hash: sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
  version: 1.0.0
  updated_at: 2026-05-01T12:00:00Z

# --- Governance Policy (ODKF v0.2 Meta-Specification) ---
# Can be a built-in profile shorthand (allow_all | zero_microdata | deny)
# or a structured reference/list pointing to external policy standards (W3C ODRL, OPA/Rego, W3C DPV, XACML):
policy: allow_all
policies:
  - type: odrl
    ref: https://www.w3.org/ns/odrl/2/policy.json
  - type: opa
    path: policies/privacy_guard.rego

# --- Digital Signatures & Cryptographic Provenance (ODKF v0.2) ---
signatures:                            # OPTIONAL. Cryptographic authorship proofs
  - key_id: did:github:andreschirinos  # Public key identity / DID
    algorithm: ssh-ed25519             # Signature algorithm
    signature: AAAAC3NzaC1lZDI1NTE5AAAAI...
    verified: true
---
```

### 14.3 Extensible Meta-Specification Contracts & Governance Policies

Because OKF/ODKF is a **meta-specification** that orchestrates existing domain standards rather than replacing them, both `contracts` and `policy` / `policies` follow an open, by-reference binding model (`type` + `path` | `ref` | `inline`):

| Category | Standard `type` Examples (Open Set) | Reference Standards | Purpose |
| :--- | :--- | :--- | :--- |
| **Tabular & Statistical Schemas** | `datapackage`, `sdmx`, `ddi`, `json_schema`, `avro`, `parquet` | Frictionless DataPackage (v1/v2), ISO 17369 (SDMX), DDI, JSON Schema | Tabular schemas, multidimensional cubes, physical units (UCUM/QUDT), value labels. |
| **Catalog & Geospatial Metadata** | `dcat`, `iso19115`, `stac` | W3C DCAT (v2/v3), ISO 19115, SpatioTemporal Asset Catalog | Public sector distributions, spatial bounding boxes, CRS projections. |
| **Service & Streaming Interfaces** | `openapi`, `asyncapi`, `graphql`, `grpc`, `flight_sql` | OpenAPI v3.0/v3.1, AsyncAPI, GraphQL, Arrow Flight SQL | Dynamic REST/RPC services, event streams, federated SQL endpoints. |
| **Executable Pipelines & Tools** | `cwl`, `owl-cli`, `okf-cli`, `cli_tool`, `dbt` | Common Workflow Language (`CommandLineTool`), semantic CLI contracts | Deterministic batch transformations, CLI parameters, output bindings. |
| **Governance & Privacy Policies** | `okf_builtin`, `odrl`, `opa`, `rego`, `dpv`, `xacml` | Built-in (`allow_all`, `zero_microdata`, `deny`), W3C ODRL 2.2, OPA/Rego, W3C DPV | Access control, $k$-anonymity cohort thresholds (`min_group_size`), differential privacy ($\epsilon$), deontic rights. |

#### 14.3.1 Semantic Correspondence Resolution (`ValueLabel` $\rightarrow$ `Concept` $\rightarrow$ `SKOS`)

To resolve semantic heterogeneity across independent datasets without hardcoding domain-specific dictionaries into the core runtime, ODKF resolves correspondences through a three-layer semantic chain:

1. **Dataset `ValueLabel` to `Concept` Mapping:** Each categorical or coded column in a dataset (`semantic_fields`) maps its raw values (`raw_value` and lexical `alt_labels`) to a local or canonical `Concept` (`concept_id`).
2. **`Concept` to `SKOS` Ontological Anchors:** Each `Concept` document defines its SKOS relationships (`skos`, `exact_match`, `close_match`, `broader`, `notation`), linking the concept to:
   - **External Ontologies:** Universal URIs such as Wikidata (`http://www.wikidata.org/entity/Q1491`), Schema.org, GeoNames, or QUDT.
   - **Cross-Dataset Concepts:** Direct references to concept documents in other datasets (`exact_match: ["censo_2024:concepts/mun_020101.md"]`).
3. **Deterministic Graph Correspondence & SQL Join Generation:** Two heterogeneous datasets $A$ and $B$ match on `ValueLabel` $v_A \in A$ and `ValueLabel` $v_B \in B$ whenever their linked concepts $C_A$ and $C_B$ either reference each other directly (`direct_concept_ref`) or share a common ontological URI in `exact_match`, `skos`, or `close_match`. The core engine compiles these correspondences into deterministic ANSI SQL `CASE ... END` projections for cross-dataset `JOIN` execution.
   
   **Transitive Match Constraint:** Because `skos:closeMatch` is inherently non-transitive and lacks cardinality constraints, automatic SQL generation MUST restrict joins to verified correspondences or `skos:exactMatch` to prevent Cartesian join explosions.

### 14.4 Canonical Triad Addressing

**Purpose & Architectural Principle:** The Canonical Triad is the unified, concise, and universal shorthand for addressing any dataset resource or executable service across the mesh. It decouples the logical reference from physical storage or network transport, allowing humans, SQL engines, and AI agents to reference data assets unambiguously.

Conforming engines, CLIs, and agents MUST support all **five canonical representations**:

1. **Canonical Colon Shorthand:** `[catalog:]dataset:resource` (e.g. `bolivia:elecciones:votos`)
2. **Path / Slash Shorthand:** `[catalog/]dataset/resource` (e.g. `bolivia/elecciones/votos`)
3. **Reverse DNS Sovereign Address:** `<dataset>.<resource>@<catalog>` (e.g. `elecciones.votos@bolivia`)
4. **Sovereign URI Scheme:** `okf://[catalog/]dataset/resource` (along with aliases `datamesh://` and `odkf://`)
5. **Direct Physical / HTTP URL:** `https://.../dataset/resource.csv` or `file:///.../dataset/resource.parquet`

#### 14.4.1 Composite Archive Subfile Addressing (`#fragment`)

All five triad forms support standard RFC 3986 fragment identifiers (`#subpath/file.csv`). When pointing to composite archive resources (ZIP, TAR), downstream runtimes use the fragment identifier to perform zero-copy, selective subfile extraction in memory (using HTTP Range requests RFC 7233) without downloading the full archive:

```text
# Examples of composite archive subfile addressing
bolivia:censo_2024:cartografia#departamentos/lapaz.geojson
okf://bolivia/censo_2024/cartografia#departamentos/lapaz.geojson
censo_2024.cartografia@bolivia#departamentos/lapaz.geojson
```

#### 14.4.2 SQL Integration & Lexical Disambiguation

Engines MUST accept single-quoted `'bolivia:elecciones:votos'`, double-quoted `"bolivia:elecciones:votos"`, and backtick-quoted `` `bolivia:elecciones:votos` `` in SQL queries, transparently mapping them to resolved paths.

**Dot Disambiguation:** When using reverse DNS notation (`<dataset>.<resource>@<catalog>`), if a dataset name contains dots (e.g., `censo.2024`), consumers MUST disambiguate by quoting or use the unambiguous canonical colon form `bolivia:censo.2024:votos`.

### 14.5 Conformance Invariants and Validation Rules

#### Producer Invariants (PE1–PE5)

- **PE1 (Markdown + YAML):** Every concept file MUST be valid UTF-8 Markdown beginning with a YAML frontmatter delimited by `---`.
- **PE2 (Mandatory `type`):** The frontmatter MUST include a non-empty `type` string.
- **PE3 (Reserved Files Integrity):** `index.md` and `log.md` MUST NOT define single-concept frontmatters; they serve directory listing and update chronologies.
- **PE4 (Syntactic Contracts Validity):** If `contracts` is specified, each item MUST declare a valid `type` and an accessible `path` (relative local path) or `ref` (absolute HTTP/HTTPS URI).
- **PE5 (Cryptographic Hash Integrity):** All declared hashes in `lineage.transformations[].hash` MUST follow the format `sha256:<hex64>` and match the computed SHA-256 digest of the referenced tool.

#### Consumer Invariants (OE1–OE5)

- **OE1 (Graceful Progressive Disclosure):** Consumers MUST be capable of parsing concept metadata from frontmatter alone without reading the entire body.
- **OE2 (Format Heterogeneity Tolerance):** Consumers MUST resolve tabular resources regardless of whether the physical target is CSV, TSV, Parquet, or JSON.
- **OE3 (Zero-Microdata Enforcement):** If a concept or resource declares `policy: zero_microdata`, consumers MUST refuse unauthenticated raw row-level scans (`SELECT *`) and permit only aggregate projections (`COUNT`, `AVG`, `SUM`, `MIN`, `MAX`, `GROUP BY`). Authenticated identities with `admin`, `analyst`, or `official` trust tiers MAY bypass zero-microdata restrictions when authorized.
- **OE4 (Canonical Triad Resolution):** Consumers MUST parse all five canonical triad representations (colon, slash, reverse DNS, sovereign URI, direct URL) including `#fragment` subfile identifiers.
- **OE5 (Air-Gapped / Offline Fallback):** When operating offline, consumers MUST resolve datasets using local cache (`$OKF_HOME/cache` or `.okf/cache`) without failing due to unavailable remote network endpoints.

#### Validation Rules (RULE-01 to RULE-12)

A conforming ODKF validator MUST execute the invariants above and report violations with severity (`ERROR` vs `WARNING` vs `INFO`):

| Rule | Check | Severity | Reference |
| :--- | :--- | :--- | :--- |
| **RULE-01** | YAML frontmatter parses correctly. | ERROR | PE1 |
| **RULE-02** | `type` is present and non-empty. | ERROR | PE2 |
| **RULE-03** | If `type == dataset`, missing `skos` is a WARNING; a malformed `skos` URI is an ERROR. | WARNING / ERROR | §14.2 |
| **RULE-04** | Every `contracts[]` entry is a map with `type` and `path` (or `ref`); unknown contract types emit WARNING; missing local paths emit WARNING (`PE4-CONTRACT-LOCAL-NOT-FOUND`). | WARNING | PE4 |
| **RULE-05** | `lineage.transformations[].hash` matches `^sha256:[a-fA-F0-9]{64}$`. | ERROR | PE5 |
| **RULE-06** | `policy` matches `allow_all`, `zero_microdata`, `deny`, or points to a valid structured policy definition / engine (ODRL, OPA, DPV). | ERROR | §14.2 |
| **RULE-07** | A bundle contains at least one concept; an empty bundle emits `RULE-07-EMPTY-BUNDLE`. Traversal detects cycles and stops (`RULE-12`). | ERROR | §11 |
| **RULE-08** | A canonical triad has 2–3 components matching `^[a-zA-Z0-9_.-]+:[a-zA-Z0-9_. -]+(:[a-zA-Z0-9_. -]+)?(#.*)?$`. | ERROR | §14.4 |
| **RULE-09** | Actor format: `generated.by` and `verified[].by` must follow canonical actor conventions (`agent:<name>`, `human:<name>`, `<email>`, or URI). | WARNING / ERROR | §7 |
| **RULE-10** | Status lifecycle: `status` must be a valid canonical status enum; if `status == superseded`, `superseded_by` is REQUIRED. | WARNING / ERROR | §5.4 |
| **RULE-11** | Temporal syntax: `expires`, `stale_after`, `cadence`, `generated.at`, and `verified[].at` must be valid ISO 8601 timestamps or durations. | ERROR | §5.5 |
| **RULE-12** | Graph integrity: Structural relations (`supersedes`, `superseded_by`, `derived_from`, `in_catalog`) must form a strict Directed Acyclic Graph (DAG) (cycle is ERROR); body navigational links allow cycles (WARNING). | ERROR / WARNING | §6.1 |

### 14.6 Ultra-Lightweight Catalog Profile (`llms.txt` / `index.md` Conformance)

To maximize accessibility, democratize data publishing, and eliminate the barrier of running heavy catalog infrastructure (e.g., CKAN, Socrata), ODKF v0.2 specifies an **Ultra-Lightweight Catalog Profile** based on plain Markdown files (`llms.txt` or root `index.md`).

#### 14.6.1 The Tri-Readable Principle

Conforming catalogs MUST satisfy three reading modalities simultaneously:

1. **Human-Readable:** Renderable in any text editor, web browser, or static file viewer without proprietary tooling.
2. **Machine-Readable:** Parsable deterministically into typed objects, extracting catalog identifiers, dataset links, resource names, and cryptographic digests.
3. **AI-Readable:** Directly consumable by Large Language Model (LLM) agents within bounded context windows, providing explicit factual grounding to prevent hallucinations.

#### 14.6.2 Canonical Syntax & Grammar

An ultra-lightweight catalog file (demonstrated in production at `https://datosbolivia.github.io/llms.txt`) MUST use the following structure. The prose and headings inside are illustrative and MAY be localized; parsers MUST key off the list-item shape, not the heading text.

```markdown
# <Catalog Name>
> <Descriptive Summary and Sovereign Scope>

<One-line statement of the catalog's scope and standard.>

## Information and Project Documentation
- [<Doc Title>](<relative_or_absolute_url>): <Summary>

## Federated Dataset Catalog (Open Knowledge Format v0.2)
- [<Dataset Title>](<relative_or_absolute_url_to_node_index_md>): <Abstract>. (Domain: <Domain Name>. Resources: <res_1>, <res_2>)
```

#### 14.6.3 Engine Conformance & Translation

Conforming consumers and SDK engines (such as `datamesh-sdk`) MUST:

1. Accept direct URLs ending in `/llms.txt`, `/index.md`, or `/catalog.yaml`.
2. Parse list items matching `- [<title>](<url>): <desc>` into registered `dcat:Dataset` instances.
3. Parse the optional parenthesized metadata in either English or the localized form (`Domain` / `Dominio`, `Resources` / `Recursos`); when present, use it to construct canonical triads (`catalog:dataset:resource`).
4. Support zero-cost hosting over static web servers, GitHub Pages, or S3 buckets without a backend database.

## 15. Decentralized & Peer-to-Peer (P2P) Sovereign Network Profile (OKF-P2P)

To eliminate single points of failure, resist censorship, and guarantee data sovereignty across federated institutions without centralized cloud providers, the ODKF profile defines an optional **Peer-to-Peer (P2P) and Distributed Network Profile** (`level-2-sovereign`). 

Core OKF bundles and Level 1 Data Products DO NOT require P2P networking; static HTTP/S, S3/MinIO, and Git repositories satisfy all operational discovery and sharing requirements. Nodes that explicitly advertise OKF-P2P conformance implement the protocol summarized here and formally specified in [RFC 0001: OKF Peer-to-Peer Sovereign Network Specification](docs/rfcs/0001-p2p-sovereign-network.md).

### 15.1 Sovereign Node Identity & Content Addressing

1. **Sovereign Node Identity (`NodeID`):**
   - Each sovereign node in the OKF network possesses an Ed25519 cryptographic key pair.
   - The canonical `NodeID` is derived as the multihash digest of the node's public key (e.g., `12D3KooW...` format compatible with libp2p PeerIDs).
   - Nodes sign all catalog announcements, metadata manifests, and resolution answers with this private key.

2. **Immutable Content Addressing (CID):**
   - Every physical resource (static Parquet, CSV, or manifest) is addressed by its cryptographic content identifier (multihash SHA-256 or BLAKE3).
   - The data address depends strictly on its bit content, ensuring zero-tampering guarantees across distributed peers.

### 15.2 Decentralized Naming & Resolution Protocol ("Sovereign Data DNS")

ODKF defines a decentralized naming and query protocol operated over a Distributed Hash Table (DHT) and cryptographic registries:

- **Reverse-Lookup Query Syntax:** `<dataset>.<resource>@<catalog>`
- **Sovereign URI Scheme:** `okf://<catalog>/<dataset>/<resource>`
- **Typed Resolution Records:** Resolution queries return typed cryptographic records:
  - `SOA`: Start of Authority (owner NodeID, public key, trust tier).
  - `CAT`: Catalog manifest pointer (CID of `llms.txt` or `index.md`).
  - `RES`: Physical resource locations (multiaddresses, HTTP, S3, Bitswap).
  - `SCH`: Syntactic schema contract pointer (Frictionless / Table Schema).
  - `LIN`: Lineage activity digest and upstream inputs.
  - `SRV`: Dynamic service endpoint (DuckDB Flight SQL, Arrow Flight).

### 15.3 Security, Sybil Defenses & Verification Boundary

1. **Integrity vs. Sybil Defense:**
   - Content hashing (SHA-256 / BLAKE3 CIDs) guarantees **immutable payload integrity** after data is retrieved.
   - However, content hashing alone **does not prevent Sybil or Eclipse attacks on DHT routing tables**. To prevent malicious actors from eclipsing discovery of sovereign catalogs, participating DHT bootstrap networks MUST employ authenticated node identity tiers (stake-weighted peer scoring, verifiable credential registries, or federated consortium keylists).
2. **P2P Zero-Microdata Policy:**
   - If a concept specifies `policy: zero_microdata`, conforming peer nodes MUST refuse binary block transfers of raw microdata to unauthenticated peers, offering instead dynamic SQL aggregate queries via Flight SQL over authenticated TLS sessions.

For full wire specifications, GossipSub topics, multiaddress transport definitions, and NAT hole-punching mechanisms, consult [RFC 0001](docs/rfcs/0001-p2p-sovereign-network.md).

## 16. Abstract Connector Architecture & Universal Standard Mappings

### 16.1 Hexagonal Port Separation Principle

Conforming to the principles of Hexagonal Architecture (Alistair Cockburn) and Domain-Driven Design (Eric Evans), the ODKF profile specifies abstract integration contracts (**Ports**) independently of any operating system, network framework, or storage engine. Concrete execution environments (such as the downstream reference runtime `datamesh-sdk`) instantiate these ports through specific infrastructure **Adapters**.

```text
+-----------------------------------------------------------------------------------+
|                        OPEN KNOWLEDGE FORMAT (SPEC.md)                            |
|                                                                                   |
|  [StoragePort]        [CatalogResolverPort]       [DataProductResolverPort]       |
|  [QueryEnginePort]    [TrustVerifierPort]         [FormatTranslatorPort]          |
+-----------------------------------------------------------------------------------+
                                         |
                       Implements / Inverts Dependencies
                                         v
+-----------------------------------------------------------------------------------+
|                       DOWNSTREAM RUNTIME (datamesh-sdk)                           |
|                                                                                   |
|  Storage Adapters:    LocalFile, HttpRange (RFC 7233), S3/MinIO                   |
|  Catalog Adapters:    GitStatic (llms.txt), LocalDir, Remote HTTP / P2P           |
|  Service Connectors:  CKAN Reader (connectors/ckan), OpenAPI, Custom Scripts      |
|  Query Adapters:      DuckDB In-Memory (Zero-Copy), Arrow Flight SQL Client       |
|  Trust Adapters:      SSH Agent, Ed25519 Whitelist, GitHub .keys, SHA-256 Digest  |
+-----------------------------------------------------------------------------------+
```

### 16.2 Normative Abstract Ports

#### 16.2.1 `StoragePort`
Abstract interface for binary content and range-based retrieval:
- `read(uri: URI) -> BinaryStream`: Retrieves complete payload.
- `range_read(uri: URI, offset: int, length: int) -> bytes`: Implements RFC 7233 byte-range reading for selective random access into composite archives (e.g., extracting central directories in ZIP files or Parquet footer metadata without full payload download).
- `stat(uri: URI) -> ResourceMetadata`: Returns content length, MIME type, ETag/hash, and modification timestamp.

#### 16.2.2 `CatalogResolverPort`
Abstract contract for traversing federated knowledge registries:
- `resolve(catalog_ref: URI | SovereignAddress) -> CatalogAggregate`: Fetches and validates a catalog manifest (supporting local directories, Git repositories, static HTTP endpoints, and Kademlia DHT lookups).
- `search(query: SearchQuery, context: TraversalContext) -> List[CatalogEntry]`: Evaluates semantic and keyword queries across federated catalog trees up to $MAX\_DEPTH=8$.

#### 16.2.3 `DataProductResolverPort`
Parses and validates multi-standard manifests:
- `parse_manifest(raw_text: str | bytes) -> DataProductAggregate`: Normalizes YAML frontmatter, JSON Schema, and Frictionless descriptors into the universal domain model.
- `validate_contracts(aggregate: DataProductAggregate) -> ValidationVerdict`: Evaluates invariant rules PE1-PE5 and OE1-OE5.

#### 16.2.4 `QueryEnginePort`
Uniform interface for zero-copy analytical execution:
- `execute_sql(query: SQLStatement, table_bindings: Dict[Triad, URI]) -> ArrowStream`: Executes ANSI SQL across local files, remote streams, and dynamic data services.
- `project(uri: URI, projections: List[str], filters: List[Predicate]) -> ArrowStream`: Pushes down column selections and row filters to underlying storage engines.

#### 16.2.5 `TrustVerifierPort`
Self-sovereign trust, cryptographic verification, and provenance checking:
- `verify_integrity(payload: BinaryStream, expected_hash: HashDigest) -> bool`: Verifies SHA-256 / BLAKE3 cryptographic integrity.
- `verify_authorship(manifest: Manifest, signature: Signature, key_locator: KeyLocator) -> TrustVerdict`: Verifies Ed25519 or SSH cryptographic signatures against sovereign trust lists or public identity services (e.g., GitHub `.keys`).

#### 16.2.6 `FormatTranslatorPort`
Near-lossless translation between OKF and external metadata standards:
- `translate(concept: Concept, target: Format) -> ExternalManifest`: Emits a DCAT-AP, Frictionless, CKAN, or Arrow/Parquet representation.
- `round_trip(external: ExternalManifest, source_format: Format) -> Concept`: Rebuilds an OKF concept while preserving unknown keys through the target's extension container (§16.4).

### 16.3 Universal Standard Mapping Table

The Open Knowledge Format functions as a meta-index bridging disparate international data specifications:

| OKF v0.2 Entity / Concept | W3C DCAT v3 | Frictionless Data Package | Apache Arrow / Parquet | W3C PROV-O | OpenAPI / Flight SQL / CWL |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Catalog** | `dcat:Catalog` | N/A (Registry) | N/A | `prov:Bundle` | N/A |
| **Catalog Record / Syndication** | `dcat:CatalogRecord` | N/A | N/A | `prov:Entity` | N/A |
| **Dataset (Domain Boundary)** | `dcat:Dataset` | `Package` (`datapackage.json`) | Dataset Namespace | `prov:Entity` | Service Scope |
| **Static Resource** | `dcat:Distribution` | `Resource` (`resources[]`) | `RecordBatch` / Parquet File | N/A | N/A |
| **Composite Resource (ZIP/TAR)** | `dcat:Distribution` (`packageFormat`) | Multipart Resource | Chunked Table | N/A | Range HTTP Endpoint |
| **Dynamic Service Resource** | `dcat:DataService` | N/A | Arrow Flight Stream | `prov:Activity` | OpenAPI 3.1 / Flight SQL |
| **Syntactic Schema** | `dcat:conformsTo` | `schema` (Table Schema) | `arrow.Schema` | N/A | JSON Schema / Protobuf |
| **Ontological Anchor** | SKOS / Wikidata (`wd:*`) | RDF Mapping Extension | Field Metadata (`ARROW:extension`) | N/A | N/A |

### 16.4 W3C Baseline Dictionary, Near-Lossless Translation and Open Extensibility

1. **W3C Standards as Default Recommended Baseline:**
   - The ODKF profile designates the official **W3C Recommendations** as its default semantic and structural dictionary:
     - **W3C DCAT v3** (`dcat:Catalog`, `dcat:Dataset`, `dcat:Distribution`, `dcat:DataService`).
     - **W3C PROV-O** (`prov:wasGeneratedBy`, `prov:wasDerivedFrom`, `prov:wasAttributedTo`).
     - **W3C SKOS** (`skos:Concept`, `skos:broader`, `skos:related`).
     - **DCMI / Dublin Core** (`dcterms:title`, `dcterms:description`, `dcterms:license`, `dcterms:issued`).
   - Consumers and agents SHOULD assume W3C semantic definitions for all standard fields unless explicitly overridden by a domain profile.

2. **Near-Lossless Translation Guarantee:**
   - When translating an OKF concept or data product across formats (OKF $\leftrightarrow$ W3C DCAT-AP $\leftrightarrow$ Frictionless Data Package $\leftrightarrow$ CKAN $\leftrightarrow$ Apache Arrow), the runtime guarantees **minimal information loss**:
     - *Syntactic Types & Invariants:* Primitives, nullability, constraints, and foreign keys are preserved.
     - *Paradata & Provenance:* Methodological attributes (`generated`, `verified`, `status`, `stale_after`, `lineage`) are preserved in designated extension envelopes (`extras` in CKAN, `custom` in Frictionless, `SchemaMetadata` in Arrow/Parquet).
     - *Zero Deletion of Unknowns:* Translators MUST NOT drop unrecognized keys; they are round-tripped through the extension container.

3. **Open Extensibility Convention:**
   - Producers are free to attach arbitrary domain-specific metadata (e.g., geospatial ISO 19115 bounding boxes, healthcare HL7/FHIR profiles, or financial SDMX dimensions).
   - Core conformance already permits arbitrary producer keys (§4.1, §11); the ODKF profile introduces no closed schema. Translators round-trip unknown keys through the target format's extension container instead of rejecting them.

## 17. Monitored Script Execution, Background Lineage Interception, and Embedded SQLite State Store

### 17.1 The Runtime Lineage Gap
Static declaration of lineage in metadata files inevitably drifts from reality as data engineering pipelines evolve. ODKF v0.2 closes this operational gap by introducing monitored runtime execution:
1. **Terminal / CLI Runner:** `okf run <script.py|script.sh|query.sql> --target <triad>` monitors execution, intercepts environment variables, standard inputs, and registers output artifacts.
2. **Function Decorator & Context Manager:** In language SDKs (Python, TypeScript, R), developers annotate functions (`@dm.track_lineage(target="dataset:resource")`) or wrap code blocks (`with dm.track(...):`), capturing inputs and computational steps transparently.

### 17.2 Embedded SQLite Operational State Store
To satisfy the KISS/YAGNI principles without an external database server,
an ODKF runtime MUST persist operational lineage in the embedded SQLite
store defined in §18.2 (`$OKF_HOME/metadata.db` or `.okf/metadata.db`,
where `$OKF_HOME` is a runtime-defined configuration directory).
The canonical schema for `executions`, `lineage_sources`,
`lineage_transformations`, and `artifacts` lives there and is not
duplicated in this chapter. The reference SDK may use `.datamesh/` for
backward compatibility.

### 17.3 Agent-Assisted Publishing Workflow
The operational SQLite store acts as the episodic memory for autonomous agents:
1. **Inspection:** Through semantic MCP tools (`datamesh_get_lineage`), an agent inspects recent execution records, artifact checksums, and upstream derivations.
2. **Synthesis:** The agent or pipeline synthesizes the attested W3C PROV-O metadata into the concept's frontmatter and its referenced `datapackage` contract (`lineage: { sources, transformations, was_derived_from }`).
3. **Publication:** The agent verifies the generated package against syntactic contracts (§14.2, §14.5) and invokes federated publication (`dm.publish`) to make the data product available across sovereign catalogs.

## 18. Federated Client Storage Architecture: Declarative Configuration vs. Operational State (`metadata.db`)

### 18.1 Storage Partitioning Principle (Human Intent vs. Operational State)

An ODKF runtime MUST maintain a strict boundary between declarative user configuration and machine-generated operational state:

1. **Declarative User Configuration (`okf.yaml` / `trust.yaml`):**
   - Explicit human intents, including catalog seed URLs, network timeouts, local workspace roots, query engine defaults (`duckdb`, `inmem`), and *Root Trust Anchors* (cryptographic author allowlists, OpenSSH public key fingerprints, verification policies `strict` vs `permissive`), MUST reside in human-readable, version-controlled YAML/JSON text files.
   - Deleting operational caches MUST NEVER alter human configuration files.
2. **Operational State & Persistent Lineage:**
   - Client runtimes manage local caching and execution lineage via an embedded SQLite database (`$OKF_HOME/metadata.db` or `.okf/metadata.db`).
   - **Architectural Boundary:** Runtimes MUST distinguish between:
     - **Disposable Caches (`cache_entries`, `dns_cache`, `keys_cache`):** Ephemeral data that can be safely purged. If deleted, the runtime self-heals by re-probing endpoints, re-fetching keys, and re-downloading resources upon next access.
     - **Persistent Lineage Ledger (`executions`, `lineage_sources`, `lineage_transformations`, `artifacts`):** The local cryptographic audit trail of computations and transformations. Runtimes SHOULD export this lineage to `log.md` or PROV-O manifests before purging local state.

### 18.2 Relational Schema & Connection Invariants

The normative relational schema for `metadata.db`, table definitions (`cache_entries`, `dns_cache`, `keys_cache`, `executions`, `lineage_sources`, `lineage_transformations`, `artifacts`), mandatory SQLite connection invariants (`PRAGMA foreign_keys = ON;`, `PRAGMA journal_mode = WAL;`, `PRAGMA busy_timeout = 5000;`), and schema migration strategies (`PRAGMA user_version`) are fully documented in [OKF Client Operational State Architecture](docs/architecture/operational-state-store.md).
